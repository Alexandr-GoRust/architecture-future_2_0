# Task4Advanced — обоснование событийного подхода (vs Camel ESB + DWH)

## Текущие проблемы интеграций «Будущее 2.0»

1. **Шина Camel — синхронные точечные интеграции**: каждый новый сервис
   (а их станет больше с фармой и электроникой) требует согласования
   контрактов и изменений у всех участников; время вывода растёт линейно.
2. **DWH как интеграционный хаб**: бизнес-логика финтеха и ИИ «захардкожена»
   в ETL внутри DWH на SQL Server 2008; сотни ТБ, отчёты часами; любое
   изменение — через команду хранилища (узкое место и единая точка отказа).
3. **Невозможность независимого развития направлений**: финтех обязан ждать
   релиза DWH; ИИ-сервисы не получают данные ближе к реальному времени.
4. **Двойной учёт и расхождения** между PowerBuilder/BI-кастомизациями и DWH.

## Что даёт событийная архитектура

| Аспект | Camel + DWH (as-is) | Событийная платформа (to-be) |
|---|---|---|
| Связанность | сильная: маршруты знают про все системы | слабая: издатель не знает подписчиков; новые потребители = новая подписка без изменений у источника |
| Time-to-market | недели/месяцы (ETL + релиз DWH) | дни: домен публикует событие по стандарту, витрина подписывается |
| Скорость данных | batch (часы) | near-real-time (секунды) — прямое требование 3-летнего плана |
| Масштабирование направлений | центральная команда DWH — узкое место | домены публикуют сами; платформа масштабируется горизонтально (партиции по агрегатам) |
| Надёжность | сбой шины/ETL валит цепочку | изоляция сбоев: retry + DLQ, подписчик не блокирует издателя |
| Аудит и происхождение | логика в ETL, непрозрачно | события — иммутабельный журнал: кто/что/когда, replay для восстановления |
| Подключение новых направлений (фарма, электроника) | перевалидация всей цепочки | подписка на события + публикация своих (стандарт и каталог схем) |

## Почему это безопасно и согласуется с этапами кейса

- **Этап 1 (0–6 мес), пилот:** финансовые расчёты или пациентский поток;
  вводим единые принципы событий, DLQ, каталог схем — и тут же получаем
  первую потоковую витрину вместо часовых отчётов (quick win для бизнеса).
- **Этап 2 (6–18 мес):** критические домены переходят на события; Camel и
  DWH остаются «мостами совместимости» за антикоррупционными слоями
  (переиздание их сообщений как событий) — легаси не трогаем до готовности.
- **Этап 3 (18–36 мес):** отказ от точечных синхронных интеграций на
  критическом пути; доменная аналитика на потоках; DWH — только архив.

## Ограничения и как их держим

- eventual consistency вместо транзакций между доменами →Saga/компенсации для
  сквозных процессов, бизнес принимает SLA согласованности;
- сложность мониторинга → трейсинг по correlationId события, DLQ-алерты;
- дисциплина контрактов → Schema Registry + CI-проверка совместимости,
  federated governance (см. Task3/Task5).

Вывод: событийный подход напрямую закрывает требования кейса — независимое
развитие направлений, near-real-time аналитика, отказ от DWH как
интеграционного центра — при контролируемом поэтапном переходе.
