# Task3Advanced — карта рисков трансформации и план управления

Целевая архитектура: `c4-target-architecture.drawio` (страница 1 — контейнеры
на горизонте 3 лет, страница 2 — компоненты витрины самообслуживания).

Ключевые решения: событийная слабосвязанная платформа (Kafka + каталог схем
+ DLQ); домены по DDD с data products (финтех, клиники, ИИ, головной офис);
витрина самообслуживания поверх Lakehouse (S3 + Iceberg + каталог DataHub);
Camel ESB и DWH SQL Server 2008 — только «мосты совместимости» с
антикоррупционными слоями и CDC, выводятся поэтапно; PowerBuilder и
BI-кастомизации заменяются порталом.

## 1. Карта рисков

| # | Риск | Категория | Вероятность | Влияние |
|---|------|-----------|-------------|---------|
| Р1 | Потеря/искажение данных при миграции с DWH SQL Server 2008 (сотни ТБ, бизнес-логика внутри DWH) | Архитектурный | Средняя | Высокое |
| Р2 | Скрытая бизнес-логика в DWH/ESB не воспроизводится в новых доменах (десятки лет кастомизаций) | Технологический | Высокая | Высокое |
| Р3 | Событийная шина становится новым «бутылочным горлышком» (единая команда владеет всем) | Организационный | Средняя | Высокое |
| Р4 | Качество данных в витрине подорвёт доверие бизнеса (противоречивые цифры со старыми отчётами) | Организационный | Средняя | Высокое |
| Р5 | Банк (регуляторные требования) не может работать в облаке/новой платформе без комплаенс-процедур | Технологический | Средняя | Высокое |
| Р6 | Сопротивление команд/дефицит компетенций (события, Data Mesh, Iceberg — новое для штата) | Организационный | Высокая | Среднее |
| Р7 | Взрывной рост объёмов/нагрузки (интеграция фармы и электроники) обгонит масштабирование платформы | Технологический | Средняя | Среднее |
| Р8 | Утечка чувствительных данных через витрину (RBAC-ошибки, широкие доступы) | Архитектурный | Низкая | Высокое |
| Р9 | Расползание сроков/бюджета: трансформация 3 года, бизнес ждёт эффекты уже через полгода | Организационный | Высокая | Среднее |
| Р10 | Vendor/инфраструктурная зависимость при переезде в облако (lock-in) | Технологический | Низкая | Среднее |

## 2. План управления рисками

| Риск | Мера | Тип меры |
|------|------|----------|
| Р1 | CDC-миграция (снапшот + накат изменений), параллельная сверка витрин с DWH на этапе пилота, версии данных в Iceberg (time travel + rollback) | Техническая |
| Р2 | Инвентаризация логики DWH (Time: Migrate/Eliminate по квадрантам TIME), антикоррупционные слои на Camel/DWH, реестр расхождений при Parallel Run | Техническая + управленческая |
| Р3 | Владение шиной — платформенная команда с SLA; домены публикуют события самостоятельно по стандартам; каталог схем и federated governance | Управленческая |
| Р4 | Data contracts + качество в CI/CD (Great Expectations), метрики качества в каталоге, «золотые» сверки со старой отчётностью до вывода DWH | Техническая |
| Р5 | Раннее привлечение комплаенс/ИБ банка; изоляция домена финтеха (свой контур/гибрид), аудит и шифрование, план по 152-ФЗ/требованиям ЦБ | Управленческая + техническая |
| Р6 | Обучение команд, наём платформенной команды, пилот на 1–2 доменах до масштабирования,_embedded_ эксперты | Управленческая |
| Р7 | Потоковые витрины + партиционирование Iceberg, нагрузочные тесты перед подключением каждого направления, автомасштабирование в облаке | Техническая |
| Р8 | RBAC витрины через Keycloak + аудит каждого запроса, sensitive-данные не попадают в curated (архитектурно), регулярные проверки доступов | Техническая |
| Р9 | Поэтапный план (пилот → критические домены → отказ от синхронных интеграций) с бизнес-результатами на каждом этапе; quick wins витрины уже в пилоте | Управленческая |
| Р10 | Открытые форматы (Iceberg/Parquet) и S3-совместимое хранилище — переносимость; минимум проприетарных сервисов в критическом пути | Техническая |

## 3. Граница технических и управленческих мер

- **Технические**: CDC/Parallel Run (Р1, Р2), data contracts и качество (Р4),
  масштабирование и потоковые витрины (Р7), RBAC/аудит/шифрование (Р5, Р8),
  открытые форматы против lock-in (Р10).
- **Управленческие**: модель владения (платформа/домены, Р3), обучение и
  наём (Р6), комплаенс-трек с банком (Р5), поэтапность с quick wins (Р9),
  приоритизация по TIME и бюджет (Р2, Р9).

Риски пересматриваются на каждом этапе трансформации (6/18/36 месяцев),
владелец карты — архитектор данных, эскалация — на архитектурный комитет.
